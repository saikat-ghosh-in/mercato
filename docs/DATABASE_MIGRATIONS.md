# Database migration contract

The raw schema-only files under `docs/sql/baseline/` came from the actual OCI PostgreSQL 14.24 databases on 22 October 2026. They contain no table data. Preserve those files as provenance. The read-only extension query in `oci-version-extensions.txt` records only `plpgsql 1.0` in each database. `V1__actual_oci_mercato_baseline.sql` uses the actual `mercato` dump; its header records the source SHA-256. Only psql restriction commands, the already-existing `public` schema creation and session-only settings were removed. No application schema was invented for V1.

The beta dump has different column and primary-key order and redundant/generated unique constraint names. V2 applies the previously recorded rich-product, marketplace, package/pricing, delivery, moderation-history and account-access scripts, then reconciles the recorded structural drift explicitly. Commission remains 0.50% or an already lower setting; historical delivery/commission snapshots retain unknown NULL values. V3 creates durable jobs and retry audit; V4 creates session authentication/MFA/abuse tables; V5 uses the PostgreSQL schema bundled with Spring Session JDBC 3.5.3; V6 records verified payment captures and gateway inbox/attempts and permits multiple refund obligations per payment.

Production uses Hibernate `validate`, OSIV disabled and Flyway validation. Automatic Flyway baselining and cleaning are disabled. Demo uses its isolated in-memory H2 schema and disables Flyway. The protected `application-local.properties` was not edited.

## Adopting an existing OCI database

1. Complete backup/restore rehearsal, stop API instances and workers, and retain a current schema-only dump made with PostgreSQL 14.24 `pg_dump --schema-only --no-owner --no-privileges`. Record server version and installed extensions separately. Keep credentials in the operator environment.
2. Compare that dump with the corresponding recorded `oci-mercato.schema.sql` or `oci-mercato_beta.schema.sql` using `backend/scripts/compare-legacy-schema.ps1`. The comparison excludes dump metadata/comments and session settings; it still checks actual SQL and ordering. Any difference fails closed and requires a reviewed migration or corrected provenance. Do not label a different existing schema as V1.
3. Only after the comparison, backup and release gates pass, explicitly register baseline version 1 using the Flyway administrative CLI with the same datasource and `-baselineVersion=1 -baselineOnMigrate=false baseline`. This writes Flyway history and does not execute V1. Never enable `baseline-on-migrate` in the application. The scripts in this repository do not perform this operation automatically.
4. Run `migrate`, validate the final application mapping and compare schema against a fresh migrated database before restarting the API. Any uniqueness/check violation requires investigation of existing rows; never delete business rows to force a migration through. Keep the application role separate from the migration owner and withhold update/delete on append-only audit tables.

Fresh empty databases execute V1 through V7 normally. V7 retains exact authenticated webhook bytes, signature and timestamp in private optional inbox columns, with an all-or-none proof constraint and a 256 KiB limit. Worker payloads remain normalized and redacted; historical/polled events retain NULL proof. These raw columns can contain provider-supplied personal data: restrict database/export access, include them only in encrypted backups, and never expose them through the operator job API or application logs. Existing unversioned schemas are deliberately rejected by normal application startup until the explicit verified adoption is performed. The adoption procedure has not been run against OCI by this work.

## Verification

`PostgresMigrationTest` applies the actual prod and beta dumps to separate populated disposable databases, verifies that automatic adoption is rejected, explicitly baselines those known fixtures and compares normalized columns/defaults/constraints/indexes/sequences against a fresh migration. It checks disabled-user retention and unknown historical snapshot values. `PostgresDurableJobsTest` checks actual PostgreSQL disjoint claims and concurrent enqueue together with the core jobs cases.

CI runs these tests through PostgreSQL Testcontainers by default and fails if Docker is unavailable; there is no skip fallback. For an explicit local PostgreSQL run, `backend/scripts/verify-postgres-foundation.ps1` reads local credentials privately and creates only random `mercato_foundation_*` databases on a loopback server. It never resets the original application database. Such a run validates a real PostgreSQL engine but does not substitute for the required Testcontainers CI evidence.
